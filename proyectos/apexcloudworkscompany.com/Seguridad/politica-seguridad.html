✅ Checklist pre-deploy

Verificar cada ítem antes de publicar cualquier sitio a producción en AWS.

✓
noindex en páginas privadas admin.html, legal/, portal/ deben tener <meta name="robots" content="noindex, nofollow">
✓
HTTPS forzado en CloudFront Behavior → Redirect HTTP to HTTPS. SSL via ACM. Verificar que el dominio no sirva HTTP en ningún path.
⚠
Tokens no hardcodeados en JS público Ningún secret, token de API, ni clave de acceso en archivos .js del cliente. Usar Apps Script intermediario o Cognito. admin.js actualmente tiene token ofuscado — migrar a Cognito cuando UserPool esté activo.
✓
Datos externos sanitizados antes de innerHTML Todo dato que venga de API, formulario o URL debe pasar por la función h() antes de insertarse en el DOM.
○
N8N webhooks con token de autenticación Cada webhook de N8N debe validar un token en los headers o body. Sin token = rechazar con 401.
○
Google Sheets con permisos restringidos Sheets de leads = acceso solo a la cuenta de servicio de N8N y al email de Garett. Nunca compartir públicamente.
✓
Formularios sin campos de pago Ningún formulario web debe pedir número de tarjeta, CVC, cuenta bancaria o datos financieros. Pagos = SINPE/Wise fuera del sitio.
○
Código fuente no en repositorio público GitHub repos de clientes = privados. El código de Apex Cloud Works no se publica sin autorización del cliente.
○
AWS IAM: principio de mínimo privilegio El usuario IAM de deploy solo tiene permisos sobre los buckets S3 correspondientes y la distribución CloudFront del proyecto. No usar el root account para operaciones de deploy.
○
Sin console.log() en producción Remover todos los console.log, console.error y datos de debug antes del deploy final.
○
CloudFront headers de seguridad activos Response Headers Policy debe incluir: X-Content-Type-Options, X-Frame-Options: DENY, Strict-Transport-Security.
Leyenda: ✓ Implementado · ⚠ Parcial/pendiente · ○ Pendiente

📋 Estándares por tipo de proyecto

🖥️ Landing Page
noindex en páginas de agradecimiento
Formulario valida campos en frontend Y backend (N8N)
WhatsApp link con número confirmado del cliente
SSL via ACM + CloudFront redirect
Rate limit en webhook N8N (N8N basic auth)
Imágenes en S3 sin acceso público directo (solo via CloudFront)
⚙️ Sistema Web
Auth via Cognito (no passwords hardcodeados)
Tokens JWT con expiración ≤ 24h
API Gateway con autenticación en cada endpoint
PostgreSQL en VPC privada (no IP pública)
Backups automáticos cada 24h (RDS o exportación manual)
Logs de acceso en CloudWatch
🤖 Automatización N8N
Webhook URL no publicada en código del cliente
Header x-token en cada llamada al webhook
Credenciales de Sheets en N8N Credentials (no en nodo)
Workflow con error handling (nodo Error Trigger)
Datos de leads no almacenados en N8N más de 24h
Test en environment de prueba antes de activar en producción

📅 Revisión mensual de seguridad

Ejecutar el primer lunes de cada mes. Tiempo estimado: 30–45 minutos.

🔒
SSL: verificar fecha de expiración Correr python security_monitor.py → confirmar que todos los certificados tengan >30 días de vigencia.
☁️
CloudFront: confirmar distribuciones activas AWS Console → CloudFront → verificar que todas las distribuciones estén en estado "Deployed" y "Enabled".
🔄
N8N: workflows encendidos Entrar a n8n.cloud → revisar que todos los workflows de clientes activos estén en estado "Active".
📊
Google Sheets: permisos de acceso Compartir → verificar que solo la cuenta de servicio de N8N y el email de Garett tengan acceso a los Sheets de leads.
🔑
Rotación de tokens Cambiar el token del Apps Script de admin si hubo acceso no autorizado. Actualizar _t en admin.js y en el Apps Script.
💾
Backup de código Hacer commit o push de todos los proyectos activos al repositorio privado. Confirmar que el código fuente está respaldado.

🚨 Respuesta ante incidentes

Si se detecta acceso no autorizado, brecha de datos o compromiso de credenciales, seguir este orden de inmediato.

Revocar credencial comprometida Si fue una IAM key: AWS Console → IAM → Access Keys → Deactivate. Si fue el token del Apps Script: publicar una nueva versión del script con token diferente.
Evaluar alcance del acceso Revisar CloudWatch Logs (si está activo) o los logs del Apps Script en Google Cloud Console. Determinar qué datos fueron accedidos.
Rotar todos los tokens relacionados Cambiar contraseña del panel admin (localStorage.removeItem('apx_g_v1') en DevTools y configurar nueva clave). Actualizar token en admin.js y Apps Script.
Notificar al cliente si aplica Si el incidente involucra datos de clientes o prospectos de un proyecto, notificar al cliente de inmediato por WhatsApp con descripción clara de qué ocurrió y qué se hizo para resolverlo.
Registrar el incidente Documentar: fecha, tipo de incidente, qué fue accedido, acciones tomadas, tiempo de resolución. Guardar en este mismo directorio Seguridad/incidentes.md.
